# D06-T11 — Add truthful PDF failure recovery

**Owner task / date:** current implementation coordinator, 2026-09-08

**Base / implementation revision:** `3219371` / `e861e14`

**Canonical acceptance:** [Document Hub PDF viewer and acceptance contract](../plans/features/2026-08-25-document-hub-ingestion-and-workbench.md#pdf-viewer), bounded to distinct shared-viewer loading/source/render failure states and safe recovery. OCR partial-state integration and parent D06 release acceptance are not claimed.

**State:** integrated; scoped local acceptance and required independent read-only QA passed. Authenticated production-data, 320/360 px, encrypted-file and forced page-render-failure browser scenarios plus deployment remain unverified.

The shared `PdfViewer` now presents named loading, password-protected, malformed, permanently unavailable file, expired/temporarily unavailable access, generic open, and page-local render failure states. User-facing copy is derived from stable PDF.js error names or safe typed signing outcomes and never displays provider messages. Encrypted and malformed files request a valid replacement; a proven missing version is non-retryable; temporary access and neutral open failures are retryable; one failed page retains its reserved slot and retries without replacing the document. Failure-state controls are disabled, loading respects reduced motion, and the viewer’s vertical bounded page stack is preserved.

Signed-source recovery follows real ownership. The Hub and compatibility modal request a new signed URL from their existing authorised caller and supply the replacement to the viewer. The canonical assigned-document route refreshes its server-owned signer and also exposes recovery when initial signing fails. RPC/query failures are typed temporary, while only an error-free lookup proving no usable grant/version becomes permanently unavailable. Provider detail remains server-side.
