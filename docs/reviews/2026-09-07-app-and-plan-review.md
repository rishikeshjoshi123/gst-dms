**CaseChain app and plan review — 7 September 2026**

CaseChain has a substantial foundation worth keeping. The overhaul has produced real document-lifecycle, provenance, recovery, Trash, identity, and Task infrastructure. However, the application is still a mixture of those newer contracts and older entry points. Some older paths bypass the intended permissions, others cannot operate correctly on canonical documents, and several approved product workflows remain unimplemented. I would not treat this checkout as ready for the confidential-data pilot.

My recommendation is to finish one safe, observable document journey and close the legacy entry points around it. Another wholesale rewrite, another architecture portfolio, or additional feature breadth would make delivery harder.

This was an assessment and a set of recommendations, not a new approved implementation plan; existing plans and in-progress edits were unchanged during the original review. On 2026-09-08, the user requested incorporation into the canonical plans. They incorporate the development-only Usage clarification, first attachment, deferred replacement UI, and single-task delivery preference. Findings and test counts below remain the historical review evidence, not a claim about a subsequently changed checkout.

**Findings that deserve priority**

1. **[P1 before a confidential-data release] Development usage tooling lacks an enforced environment/operator boundary.** The user clarified that aggregating usage across testing members is intentional development behavior, and the planned separate platform-admin view owns the eventual replacement. This is a release-cutover gap, not a criticism of that development requirement. The current `/usage` page checks authentication, then uses the service client to select usage rows across all organisations, including document references, and passes those rows into a Client Component. There is no executable development-only or platform-operator guard. Separately, `updateModelPricing` checks an ordinary organisation-admin role and uses the service role to upsert global prices. The new platform tables do not protect these old entry points. Preserve the intended metering in the isolated development environment; before confidential-data release, enforce the environment/operator boundary or disable the legacy routes and actions. The full platform console need not ship merely to deny those legacy paths. Hiding the navigation item alone is insufficient. Evidence: [usage reader](/Users/rishikeshjoshi/Desktop/dms/src/app/(app)/usage/page.tsx:16), [pricing action](/Users/rishikeshjoshi/Desktop/dms/src/lib/actions/pricing.ts:17). This is consistent with Supabase's documented [service-role RLS bypass](https://supabase.com/docs/guides/troubleshooting/why-is-my-service-role-key-client-getting-rls-errors-or-not-returning-data-7_1K9z).

2. **[P1] Viewer permissions are not enforced end to end.** Client creation/update use the service role after checking authentication and organisation membership, without a mutation capability check. Legacy client/matter/document write policies also accept `is_org_member`, whose canonical replacement includes active Viewers. Several document columns retain authenticated write grants. Fixing only the service-role calls would therefore leave a second route around the intended Viewer ceiling. Apply the capability contract to both database grants/policies and application commands, and test the actual exported actions/direct API paths as a Viewer. Evidence: [client creation](/Users/rishikeshjoshi/Desktop/dms/src/lib/actions/client.ts:55), [client update](/Users/rishikeshjoshi/Desktop/dms/src/lib/actions/client.ts:107), [legacy write policies](/Users/rishikeshjoshi/Desktop/dms/supabase/migrations/00014_fix_delete_rls.sql:25), [canonical membership predicate](/Users/rishikeshjoshi/Desktop/dms/supabase/migrations/00030_organisation_invitations_and_membership_rls.sql:238), [document column grants](/Users/rishikeshjoshi/Desktop/dms/supabase/migrations/00071_current_provenance_search_and_embedding_privileges.sql:94). These are source-confirmed authorization gaps, not a remotely executed exploit.

3. **[P1] Any member who can read a note can reach a service-role deletion path.** `deleteNote` verifies that the note and its Matter are readable/active, then soft-deletes through the service client. It never checks the note author, role or deletion capability. This bypasses the ordinary note update policy, which requires author or admin. Even after the Viewer issue is addressed generally, an Associate must not gain the ability to delete someone else's note merely by reading it. Use a caller-authorized command, include resource-state checks inside the mutation transaction, and test author/non-author/Admin/Viewer cases. Evidence: [deleteNote](/Users/rishikeshjoshi/Desktop/dms/src/lib/actions/notes.ts:247), [note update policy](/Users/rishikeshjoshi/Desktop/dms/supabase/migrations/00002_rls.sql:267).

4. **[P1] The default production build fails locally because application code imports worker implementation.** On a clean lockfile installation with Node 24.8.0, `next build` fails at `@napi-rs/canvas/js-binding.js` with “non-ecmascript placeable asset.” The import trace runs from the Dashboard/document actions through the outbox wake helper into Trigger workers and native PDF acquisition. The application should enqueue the fixed dispatcher task through a small SDK adapter; it should not import the worker's dependency graph to wake it. Keep native parsing in the worker boundary and configure intentional native server dependencies explicitly where still needed. Recheck on the deployment OS as well. Evidence: [wake import](/Users/rishikeshjoshi/Desktop/dms/src/lib/outbox/wake.ts:22), [worker imports](/Users/rishikeshjoshi/Desktop/dms/src/trigger/outbox.ts:1), [native PDF adapter](/Users/rishikeshjoshi/Desktop/dms/src/lib/documents/native-pdf-pages.ts:1). This is a reproduced local build failure, not a claim about the currently deployed revision.

5. **[P1] The promised upload size exceeds the documented Vercel transport limit.** Both upload entry points send the file in FormData to a Server Action; the action receives and transfers the entire PDF. `next.config.ts` raises Next's buffers to 27 MB, but Vercel documents a 4.5 MB function request/response limit. The repository's portal plan identifies Vercel as the app host, and the pilot corpus includes PDFs up to about 7 MiB. Those larger uploads will hit the host boundary if this transport is deployed there. Implement the already-planned reserved direct-to-private-storage upload, followed by authoritative server verification/finalization. Validate actual deployed boundary sizes, not only config strings. Evidence: [upload action](/Users/rishikeshjoshi/Desktop/dms/src/lib/actions/document.ts:110), [upload configuration](/Users/rishikeshjoshi/Desktop/dms/next.config.ts:6), [Vercel limits](https://vercel.com/docs/functions/limitations). This conclusion is conditional on the documented Vercel hosting arrangement; deployment configuration was not inspected remotely.

6. **[P1] Historical source viewing and quotation do not preserve a consistent evidence context.** The canonical route can sign a requested historical version while still loading current effective metadata and passing it into the editable inspector. There is no clear historical-version presentation at that boundary. Separately, the viewer's global quote event carries only text/page, and the note writer receives document ID/text/page without immutable version identity. After replacing a PDF, the same note can lead to a different source page. Pass the selected version through the entire viewer/inspector/quote contract; explicitly label current versus historical interpretation, and prevent misleading current-value edits from a historical view. Evidence: [source selection versus metadata](/Users/rishikeshjoshi/Desktop/dms/src/app/(app)/documents/[docId]/page.tsx:36), [quote event](/Users/rishikeshjoshi/Desktop/dms/src/components/ui/pdf-viewer-client.tsx:70), [note creation](/Users/rishikeshjoshi/Desktop/dms/src/components/matters/TimelineDocumentDetail.tsx:174). Page URL restoration is a useful completed slice, but it is not yet durable citation integrity.

7. **[P1] Review can hide a problem without making a documented decision.** `dismissReviewFlag` changes the document status to `analyzed` and clears the reason. It does not resolve a typed Review item, record evidence/reason/decision, or reconcile field decisions. The live Review UI exposes it as successful dismissal. This does not prove invalid candidates become effective—the provenance foundation provides separate protections—but it does remove the visible exception without resolving the underlying issue. Connect the minimum real extraction/placement/duplicate/recovery Review flow before claiming the pilot's human-review safeguard is complete. Evidence: [dismissal action](/Users/rishikeshjoshi/Desktop/dms/src/lib/actions/document.ts:452), [live Review UI](/Users/rishikeshjoshi/Desktop/dms/src/app/(app)/review/ReviewClientView.tsx:67), [approved decision contract](/Users/rishikeshjoshi/Desktop/dms/docs/plans/features/2026-08-25-work-review-activity-notifications.md:89).

8. **[P1] The Matter identity constraint still prevents two matters for one client in the same financial year.** `idx_matters_unique_client_fy` remains in the migration chain, with no later removal found. It applies to every non-deleted Matter, including closed matters. That means even manually creating a second independent proceeding for the same client/year is rejected. The Document Hub plan correctly identifies this as an unsafe long-term identity assumption. Prioritize the replacement proceeding/matter-identifier contract, and update restore conflict logic as part of that change. Evidence: [unique index](/Users/rishikeshjoshi/Desktop/dms/supabase/migrations/00020_matter_uniqueness.sql:9), [restore's matching assumption](/Users/rishikeshjoshi/Desktop/dms/supabase/migrations/00088_root_scoped_trash_restore.sql:215). Do not casually drop the index without replacing its duplicate/identity safeguards.

9. **[P2] Move and Copy still use incompatible legacy document operations.** Copy downloads through the caller's Storage client; canonical asset paths contain the organisation ID as their second path segment, while the surviving `docs_read` policy expects a Matter ID there. Canonical copies therefore cannot normally read their source through this path. The older copy branch also creates a document without its canonical file version. Move deletes links before updating the document, then updates deadlines separately without handling that result. A later failure can leave a partially changed record. Replace these with the planned atomic, asset-reusing lifecycle commands; do not just grant broader Storage access to make the old copy work. Evidence: [copy/move action](/Users/rishikeshjoshi/Desktop/dms/src/lib/actions/document.ts:286), [Storage policy](/Users/rishikeshjoshi/Desktop/dms/supabase/migrations/00003_realtime_storage_triggers.sql:55).

10. **[P2] A legitimately emptied Document Hub remains visibly populated.** The reader returns `[]` for both an empty queue and an error. The client compensates by retaining old rows whenever a populated queue refreshes to empty. If another user assigns/discards the last item, or background processing removes the last intended-Matter item, the old user keeps stale rows and receives an error-like message. Give the reader an explicit success/error result and accept a successful empty snapshot. The current Task-reader changes already provide a useful example of separating failures from valid empty data. Evidence: [reader](/Users/rishikeshjoshi/Desktop/dms/src/lib/actions/inbox.ts:27), [state preservation](/Users/rishikeshjoshi/Desktop/dms/src/app/(app)/documents/DocumentHubClientView.tsx:225), [refresh handling](/Users/rishikeshjoshi/Desktop/dms/src/app/(app)/documents/DocumentHubClientView.tsx:319).

11. **[P2] A late PDF request can replace the source for a different selected row.** `openSource` captures a selected Intake item, awaits signing, then unconditionally sets the source URL. Selecting another row clears the URL but does not cancel/fence the earlier request. A slow response can display document A next to document B's details. Bind asynchronous results to the selected item/request generation and discard obsolete results. Evidence: [selection and source request](/Users/rishikeshjoshi/Desktop/dms/src/app/(app)/documents/DocumentHubClientView.tsx:296).

12. **[P2] Completed Tasks can remain open in the legacy Review queue.** The new Task authority intentionally does not dual-write completion into `case_notes.action_item_resolved`. The Review reader still filters that legacy flag. Completing a migrated action item in Tasks therefore does not remove it from this old Review projection. Remove note tasks from Review as already planned, and read current Task state everywhere it is displayed. Evidence: [legacy Review query](/Users/rishikeshjoshi/Desktop/dms/src/lib/actions/notifications.ts:302), [approved Task-only authority](/Users/rishikeshjoshi/Desktop/dms/docs/plans/features/2026-08-25-work-review-activity-notifications.md:211).

13. **[P2] Overdue deadlines disappear from the attention query, and reminders are not implemented.** The Dashboard deadline reader filters `due_date >= today`, excluding unresolved overdue dates. The `deadline-reminders` task is a placeholder returning `{ checked: true }`; its name/comment does not constitute a scheduler or delivery capability. Make overdue work visible before building richer calendars. Keep reminder readiness truthful until verification, recipients, dedupe and delivery are complete. Evidence: [date filter](/Users/rishikeshjoshi/Desktop/dms/src/lib/actions/notifications.ts:265), [placeholder task](/Users/rishikeshjoshi/Desktop/dms/src/trigger/jobs.ts:412).

14. **[P2] The actual PDF viewer does not satisfy the mobile design contract.** In a browser specimen using the real component and a valid synthetic PDF, the 320px pane clipped the page/zoom toolbar and source text. The viewer has an unwrapped fixed-width toolbar, a 600px minimum body inside constrained panes, and no fit-to-width behavior. It also hardcodes a white toolbar and uses only mouse-up text selection. The assigned-document desktop layout allocates 65% + 35% widths with non-shrinking children plus an additional gap, which can clip the inspector. Fix the shared viewer and its real consumers, then test 320px, 360px, short-height desktop, touch selection, dark mode and 200% zoom. Concept acceptance at 460px does not validate this separate production component. Evidence: [viewer](/Users/rishikeshjoshi/Desktop/dms/src/components/ui/pdf-viewer-client.tsx:84), [document pane layout](/Users/rishikeshjoshi/Desktop/dms/src/app/(app)/documents/[docId]/page.tsx:86).

**Release-policy gaps and further improvements**

The pilot boundary currently exists more clearly in prose than in executable configuration. Signup/onboarding can create a new organisation without a pilot invitation/allowlist gate in the application command. CaseWiki still exposes `triggerWikiGeneration`, which schedules a provider-backed worker after checking read access, despite the pilot documents saying generation is disabled. Permanent deletion and automatic retention also exist while the pilot sequence says destructive automation is unavailable. The newer Trash contract may reflect a deliberate change of intent; reconcile that conflict explicitly rather than assuming which paragraph wins. Use one reviewed pilot capability/route matrix enforced at loaders, commands, direct APIs and workers. A disabled control must also be unavailable through its server entry point. Evidence: [organisation creation](/Users/rishikeshjoshi/Desktop/dms/supabase/migrations/00108_single_current_organisation_task_authority.sql:58), [Wiki trigger](/Users/rishikeshjoshi/Desktop/dms/src/lib/actions/wiki.ts:71), [pilot contract](/Users/rishikeshjoshi/Desktop/dms/docs/plans/operations/2026-08-29-design-partner-pilot-execution-sequence.md).

The team-directory privacy boundary is inconsistent. Settings consumes `get_my_team_members`, which can withhold email addresses, while the Matter page and Notes/Activity readers still call the global Auth admin directory and reconstruct member/author emails. The Matter page filters returned users to organisation members, so this is not evidence that it returns the entire global directory to the browser. It does, however, bypass the approved email projection and relies on an unpaginated privileged lookup. Reuse the canonical directory projection and immutable actor snapshots. Evidence: [Matter loader](/Users/rishikeshjoshi/Desktop/dms/src/app/(app)/matters/[id]/page.tsx:54), [canonical Team projection](/Users/rishikeshjoshi/Desktop/dms/supabase/migrations/00036_document_upload_commands.sql:31).

The performance model should change before collections grow. Document Hub loads all matching Intakes and all Matters; the sidebar count loads the Intake rows again. The Matter route eagerly loads every section, document, note and member before rendering; a document page loads the Matter's documents/relationships for its inspector. These costs scale with the whole Matter or organisation instead of the active task. Introduce bounded collection projections and server pagination, a true count query, lazy active-section loading, and inspector reads limited to the selected document and required relationship context. Keep the initial pilot implementation modest; a new generalized query framework is unnecessary.

Realtime is currently uneven. Matter subscribes to broad RLS-visible table changes and filters in the browser; the new Document Hub relies on manual refresh. The approved design calls for scoped invalidations and authoritative reconciliation. Prioritize intake progress and Review claim/decision freshness, where stale state changes a user's next action. Do not roll out a global socket merely for counts. Also refresh effective inspector metadata with document state; refreshing only document rows leaves a second, stale metadata projection beside them. Evidence: [Matter subscriptions](/Users/rishikeshjoshi/Desktop/dms/src/components/matters/MatterTabs.tsx:67).

Search is still a navigation lookup. The live action returns Client/Matter/Document links and optionally uses transitional whole-document vectors; it does not expose the new page chunks, citations or typed numeric/legal constraints. Its offline baseline explicitly models a future target and is not evidence of current retrieval quality. Deliver exact references and dependable lexical lookup first, then the approved Matter-scoped cited retrieval after the OCR gate. Avoid making users choose “semantic” versus “ordinary” search, and show source coverage rather than a similarity percentage.

The AI direction is largely sound. Source-grounded critical-field verification, immutable candidates and preserved human decisions address the real trust problem. The remaining evaluation should measure routing errors, exact critical facts, evidence-page/anchor correctness, table structure, failure handling and review burden separately. A small error-free corpus is an acceptance gate, not proof of zero future errors. Preserve hard cases as regression fixtures and measure human correction time; a system that extracts many fields but needs several minutes of correction per PDF may not improve the partner's work. No confidential corpus processing was performed in this review.

There are inexpensive usability improvements worth making alongside those workflow changes: normalize CaseChain/GST Litigation DMS naming; use “Move to Trash” instead of permanent-delete language for recoverable actions; preserve Matter section/selected document in URLs; reserve real action labels instead of relying on native title tooltips; describe user outcomes instead of “canonical pipeline”; and make unavailable permissions explicit rather than offering actions that fail afterward. These are best fixed in shared components and the affected real flow, not through another round of isolated mockups.

**Critique of the plans and execution process**

The plans contain good decisions. Separating source evidence from legal interpretation, using durable work, preserving human corrections, distinguishing Review from Tasks, and keeping legal dates/amounts provisional are all worth retaining. The pilot execution sequence also correctly proposes vertical delivery. The problem is that the status and acceptance process do not reliably show whether those decisions are connected to the app a person can use.

There is a concrete arithmetic error: the portfolio table contains **7 approved, 6 in-progress, and 1 not-archived** child domain, while its following paragraph and the index claim **9 approved, 4 in-progress, and 1 not-archived**. Across all 18 archived plan files, frontmatter says **7 approved, 8 in-progress, 3 proposed, and 0 completed**. These are different populations, but neither supports the portfolio's stated 9/4 split. Evidence: [portfolio table and count](/Users/rishikeshjoshi/Desktop/dms/docs/plans/platform/2026-08-24-product-architecture-portfolio.md:123).

Plan status also mixes design approval with delivery. Document Hub is `approved` despite several implemented checkpoints; Trash is `approved` while its maturity text says no further action is queued. Historical “Current-state audit” sections still describe upload paths that newer checkpoints have replaced. The pilot sequence still starts from old commit checkpoints. `docs/project-portal-status.json` is stale, but the current portal builder does not consume it as its delivery dashboard; updating that file alone would not solve visibility.

I suggest keeping the archive as the decision record and adding one small, generated delivery ledger. For each user capability, record: approved contract, current implementation state, enabled routes/roles, deployed revision/environment, last passing acceptance evidence, active blocker, and next observable outcome. Generate aggregate counts instead of maintaining them in several paragraphs. Label historical audits with their date and keep a short current-state summary. Preserve the existing status vocabulary rather than inventing another competing set of plan files.

The scope is large for the first design partner: the archive has 5,187 lines of plans, and the migration chain has about 30,300 lines. Size alone is not a defect, and migration count is not a completion metric. However, this is a meaningful maintenance commitment. Departure notices, advanced purge governance, a full operations console, sophisticated financial history, a graph, cited Brief maintenance and a comprehensive interactive demo should not all compete with the first reliable document journey. Keep their decisions, but activate only the work justified by the pilot contract and immediate user feedback.

The open approval queue should be prioritized by release dependency. Review's visual direction and OCR thresholds affect the main journey. Broader Associate grant design and advanced departure presentation can remain deferred if the pilot's enabled capabilities are correspondingly narrow. “Continue independent work” should mean work that improves the intended release, rather than an unlimited succession of additional foundations.

Independent QA remains useful, but evidence should attach to a revision and executable scenario. Repeated source-only checks of small tranches cannot establish that the combined app compiles, deploys, preserves permissions and completes a workflow. Of 46 TypeScript test files examined, 24 contain `readFileSync` source assertions. Many of those tests also contain useful behavioral checks; the count is not a claim that they are all superficial. Nevertheless, source-shape checks cannot catch host upload limits, worker bundling, role bypass through a different action, a stale queue, or clipped PDF controls. Retain them as guardrails and add a small number of real integration journeys.

The repository CI presently checks migration names before pushing to the configured remote, then regenerates types. I found no repository workflow enforcing application tests, typecheck, lint, build, clean SQL replay and acceptance before that push. Establish that gate, pin the package manager/runtime, and keep type generation deterministic. The installed lockfile dependencies include Node >=22 requirements while this shell defaults to Node 20; the plans already call for Node 24 worker alignment. The current broken mixed dependency tree and missing root links make everyday verification unreliable.

**Recommended delivery order**

1. Close exposed authorization paths and make the default build/typecheck reproducible. Deny unsupported high-consequence entry points. Add direct action/API tests for Viewer, non-author Associate, removed member and another organisation.
2. Write down the exact pilot-enabled routes and operations. Reconcile signup, CaseWiki and purge with that boundary. Use the existing pilot plan as the owner of this decision.
3. Finish one thin document journey: invited user → upload → visible progress → material exception → evidence-backed decision → placement → Matter reopening → exact source. Include duplicate, failed/retried upload, replacement, revoked access, a second browser session and a phone viewport.
4. Deliver the bounded Matter shell, chronology and Files view around that journey. Load the active section only. Keep the richer graph and remaining breadth behind their later gates.
5. Complete the approved OCR benchmark and connect Matter-scoped cited Search. Validate retrieval on held-out representative cases, not just the offline model's expected IDs.
6. Rehearse the exact release in its deployment environment, including large uploads, workers, email entry, missing objects, monitoring and rollback. Preserve the expressly approved first-pilot backup limitation; do not silently replace it with an unapproved stronger recovery promise or claim a restore drill has passed.

Measure document upload-to-reopen completion, actionable failure/recovery, time spent correcting/placing each PDF, exact citation-open correctness, and successful repeat retrieval by the partner. Those will tell you more about product improvement than the number of migrations, concepts or approved plans.
